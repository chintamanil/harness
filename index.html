AIDLC AUTOPILOT HARNESS

An end-to-end SDLC harness that drives a requirement from plan to merged PR through eight coordinating agents — where the review gates are executable code, not prompt instructions.
The design question throughout: which guarantees does a machine actually check, and which did we merely ask an agent to honor?

8 COORDINATING AGENTS
14 FAIL-CLOSED GATES
3 BOUNDED LOOPS
0 UNBOUND MERGES
The Core Idea

ASKED VS. CHECKED

The harness is two different kinds of thing, and the boundary between them matters more than anything inside either half. Four phases are prose — markdown skills an agent reads and is asked to honor, ending in a human checkpoint. One phase is code — a JavaScript workflow that checks schemas, SHAs, sizes and merge conditions mechanically, whatever an agent claims. An asked-for guarantee feels identical to a checked one — right up until it fails.

Why it matters
  • A guarantee in the prose half is one an agent was asked to honor. A guarantee in the code half is one the JS checks.
  • Every serious defect found while building this was a place where the first kind had been mistaken for the second.
Consequence for design
  • Anything load-bearing migrates from prompt text into a schema, a comparison, or a gate reason.
  • Prompts still matter — they shape judgment. They just stop being where correctness lives.
The checkpoint, precisely
  • D · Checkpoint is once per run, not once per PR — it gates whether execution starts at all.
  • Whether an individual PR merges without a human is decided far later, by the merge gate in stage C.

Same rules, different guarantees
  • Both paths read the same fix-discipline reference — the rules are identical. Only the workflow path can prove they were followed.
  • A hand-driven session that narrates the red-first step without doing it produces exactly the fix the enforcement exists to catch.
What to do about the weak path
  • Treat a hand-driven session's closure claims as claims — the next review round audits them against the remediation contract instead of trusting the narration.
  • This asymmetry is the site's core idea in miniature: identical prose, and correctness lives only where the code checks it.
Execution Topology

ADMIT · BUILD · MERGE

The code half is three blocks in sequence. Everything read-only happens in A, so a run that stops there has mutated nothing — which is what makes a dry run trustworthy rather than merely well-intentioned. B is a pipeline with no barrier between stages, so one item can be in red team while another is still being implemented. C is deliberately serialized: one PR at a time.

Bound 01
4 items per run
Work is discovered in full, then capped as whole groups — never a partial group, because a half-executed epic is worse than an unstarted one.
Bound 02
3 fix attempts
Each is a fix plus an independent re-review, never the fixer self-reporting clean. Exhausting them routes to a human.
Bound 03
3 red-team rounds
Measures whether the defect surface converges, not whether it is empty. Round 2 finding what round 1 missed is the real signal.
The rule that ties them together
  • Running out of attempts is itself the signal for a human — never a reason to merge.
  • Every dotted exit is fail-closed: the run stops and reports rather than guessing at intent.
  • The guard between A and B is asymmetric on purpose: unproven model routing stops the run (two reviewers might be the same model), while unproven isolation only degrades it — the build proceeds, but host test dispatches are withheld and nothing auto-merges.

Deep Dive

THREE LOOPS THAT MATTER

Most of the harness is plumbing. Three components carry the actual safety properties, and each one exists in its current shape because a simpler version failed in production.

B3 — THE FIX LOOP, RED FIRST

one fix attempt — order is enforced, not suggested

The failure it prevents
  • A test written in the same pass as the fix, from the same misreading of the defect, encodes the misreading twice and goes green.
  • The reviewer's reproducer is the only oracle that comes from outside the fixer's own interpretation.
Made mechanical
  • The fixer must return a reproducer it observed failing before the fix; a missing row becomes a merge-gate reason.
  • What is checked is absence, not honesty — no reproducer proves the step was skipped, whatever the agent asserts.

B5 — RED TEAM, CONVERGENCE NOT CLEANLINESS

Counterintuitive by design
  • Red-team findings never block a merge, at any severity — they become tracked issues and the PR ships.
  • What blocks is divergence: a defect surface that grows under repeated attack is one nobody has bottomed out.
Coverage as evidence
  • One agent covering five lenses can silently blur or skip one, and a per-finding label cannot detect that.
  • So each lens must return a coverage row — "ran and clean" and "never ran" must not look identical.

Why the decision has no agent in it
  • Size, risk and reviewability are computed from the mechanical diff — never from a review agent's prose summary of it.
  • An agent can be persuaded by a well-written PR description. A line count cannot.
Merge Policy

WHEN A HUMAN IS ASKED

An empty reason list means the PR merges with no human at all — the normal outcome for a clean change. Everything below is a statement about evidence we do not have, not about defects we do.

Class 01
Evidence integrity
A review artifact missing, unbound, stale or shallow. An unproven capability claim. A weak test oracle. CI unreadable for the gated commit. Isolation unproven with no green CI to substitute.
Class 02
Impact and reviewability
Over 1,000 production changed lines. A risk-area path or content match. A safety control deleted from production code. Model routing unproven, so two reviewers may be the same model.
Class 03
Decisions, not defects
A finding marked ask-user — it challenges deliberate intent or changes product behavior. Blocks at any severity, because the question is who may resolve it, not how bad it is.
The distinction people get backwards
  • Red-team findings do not block. A defect that is written down and owned is not a reason to stall a PR.
  • Review verdicts do block. A rejected review is not a defect list — it is a reviewer saying it could not establish the change is correct.
Why that asymmetry is right
  • Tracking a known bug converts it into scheduled work; that is progress.
  • Merging on "we could not verify this" converts uncertainty into "we shipped it, see ticket". That is not.
Two independent axes
  • action routes a finding; severity ranks it. Neither is derivable from the other.
  • A low-severity finding can need a human decision; a high-severity one can be cleanly auto-fixable.

THE SIZE GATE — TWO COUNTERS, ONE BLOCKS

Production lines block at 1,000
  • Additions plus deletions, never net. More production code is more places to be wrong — that is risk, so it is a hard limit.
  • Docs, tracker state and CHANGELOG are excluded. Lockfiles, dist/ and generated clients deliberately are not — they change runtime behavior.
Total lines only advise at 2,500
  • Production + tests measures reviewer attention — a capacity concern, and blocking is the wrong answer to "this is a lot to read".
  • Kept as two separate functions so a caller cannot concatenate them and promote attention-cost back into a merge blocker.
Tests can never block
  • Test lines are excluded from the blocking count, so writing more tests never pushes a PR toward a human gate.
  • The old 400/800 pair did exactly that — perverse in a repo whose contract mandates TDD. On one measured PR, a modest 1.3:1 test ratio blew the old total budget by 464 lines while production was over by only 123.
Predicted at the dry run
The only structurally-unfixable blocker
A size finding means "this should have been decomposed differently" — a decision made two phases earlier. Discovering it at the merge gate wastes the entire execute → review → peer → red-team spend, so each PR group carries a predicted size, and any group above 12 production files is flagged at the checkpoint, where splitting is free.
Files, not lines
No fabricated precision
Nothing has been written yet, so a predicted line count would be invented. The threshold is an explicit heuristic; crossing it means "look at this grouping", never "this will fail". And it adds no gate — the dry run already ends at a human, so the prediction only has to be visible. "Unknown" is reported as unknown, not as small.
Execution Evidence

WHAT COUNTS AS PROOF

Two questions decide whether a change was ever actually executed before it merges: does CI count as evidence, and may anything run on the host? Both answers are mechanical, and both fail closed — but one of them had to stop failing stuck.

ciGreen — required checks, and the no-admin fallback

Fail-closed became fail-stuck
  • Marking a check required needs repository admin. With push-only permission that state can never become true — so hard-blocking on it meant every PR human-gated forever, regardless of quality.
  • The fallback is deliberately stricter than the required path: with no required set, nothing defines which checks were expected, so anything short of "every observed check green" blocks.
The hole, closed elsewhere
  • The one thing branch protection uniquely buys is stopping a PR from disabling its own checks.
  • Closed independently: any change under .github/ is a first-class risk area and can never auto-merge, whatever CI says. That dependency is load-bearing, so a test reddens if it is removed.
Scope limit — read before reusing
  • The fallback was an explicit human decision for non-production repositories. It is not a general improvement.
  • Before pointing this at production: restore the hard required-checks rule, or gate the fallback on the resolved repository owner.

RUNTIME ISOLATION — THE HONEST CLAIM

Mechanically enforced
  • The workflow's own dispatches that execute repo-controlled commands — the declared test runner and the post-merge integration test — each carry an explicit isolation guard.
  • In degraded mode neither can fire. No prompt can talk past this.
Requested only — asymmetric by design
  • Code-writing stages are asked not to run the suite. Reviewing stages are permitted execution under a stated containment posture — because verification requires execution.
  • On one PR the review marked a compatibility claim PROVEN from static reading; the peer REFUTED it by running a probe. Withholding execution from reviewers would have shipped that defect.
Said precisely
  • The honest claim: workflow dispatches cannot fire, writers are asked, reviewers execute under posture. Never "repository-controlled execution is withheld".
  • Closing that gap needs a command broker or a container — not stronger prompt wording. Worktree isolation separates files, not credentials or network.
Failure Modes Found and Fixed

WHAT ACTUALLY BROKE

Each of these was a confidently-worded guarantee that did not hold. They are the reason the harness looks the way it does, and every one is now pinned by a test that fails if the fix is reverted.

Defect 01
A check that passed vacuously
Reviews are bound to a commit SHA, and the gate compared the artifact's SHA to an independently-read one. But the comparison was guarded by if (expected && ...) — so when the independent read failed, the check silently passed. The guarantee evaporated in exactly the situation it existed for. Now a missing expected value is a blocking reason, not a skipped comparison.
fail-openSHA bindingmutation-pinned
Defect 02
Two Opus reviews, one discarded
The red-team loop re-ran a full peer review after every attack round that fixed something. Nothing in the loop read that verdict, and each round overwrote the last — so on a three-round PR, two expensive reviews were produced and thrown away. Hoisted to a single review after the loop, on the final commit. Identical coverage, since it reviews the whole diff rather than an increment.
wasted computeloop hygiene
Defect 03
A rule that fought its own detector
Divergence was detected by hashing severity|file|summary. Meanwhile the prompt required re-reporting an unfixed finding "at the same or higher severity" — which changed the hash, registered as a brand-new defect, and sent a correctly-behaving run to a human. Following the instruction guaranteed a false alarm. Now keyed on a stable finding id.
false positiveprompt vs code
Defect 04
One threshold, four copies, two stale
The reviewability limit lived as prose in four files. Two still carried a superseded 400/800 pair. The costly one instructed the decomposer to target the old limit — so it split work into more PRs than the gate required, and every extra PR paid a full review, peer and red-team cycle. Reconciled, with a shared reference as the single owner.
doc driftreal cost
Defect 05
Fixes that closed nothing
A remediation round reported six findings closed; the next review round found all six still live, plus new defects the fixes had introduced. Root cause was structural, not a capability limit: the same agent wrote the fix and the test that was supposed to prove it, from one shared misreading. The countermeasure is ordering — the reviewer's reproducer becomes a failing test first.
weak oracleshared mental model
Method
Every gate is mutation-tested
A passing test proves nothing until you have seen it fail. So each gate is verified by reverting the enforcing line and confirming a named assertion goes red. One refinement earned the hard way: check which assertion went red — a mutation that breaks a cache key so nothing is ever stored kills the reuse test while leaving the correctness test untouched, and the correctness test is the one that matters.

Outcomes

MEASURED, NOT ESTIMATED

Every number here is something the code demonstrates or a test enforces. Token-cost claims are deliberately absent — per-phase accounting has not been instrumented, so any percentage would be a guess dressed as a metric.

Correctness
  • An unbound or stale review can no longer reach a merge — the binding is re-asserted at every phase boundary.
  • An unclassified finding fails closed to "needs a human" rather than being swept into an automated fix.
Cost
  • The diff read went from one command per changed file to one for the whole range — same bytes, a fraction of the turns.
  • Memoized on the commit SHA, so a fix round that legitimately changes nothing stops paying for an identical re-read.
Throughput
  • Findings became tracked work instead of merge blockers, which removed the stall the loop existed to drain.
  • Oversized groupings are now predicted at the checkpoint, where splitting is free — not at the gate, after the work is done.
Maintainability
  • Shared references own each rule once; four callers point at them and none restate them.
  • An install script verifies frontmatter, references, parse and the offline suite after every update.
Deliberately not memoized
The final SHA read
Its two merge-phase calls look redundant and are not: the first gates, and the second exists solely to detect drift since that gate, immediately before merging. Caching it would delete a safety check, not save a token.
Deliberately not shared
The in-memory diff
Handing the workflow's own copy of the diff to all three reviewers is the largest saving available — and not taken, because they would all read one mechanical agent's copy. A subtly wrong copy blinds them identically: opus rates for correlated opinions. Reviewers fetching independently is what lets them fail differently.
The transferable lesson
  • Agent reliability is an architecture problem, not a prompt-quality problem. The wins came from moving guarantees into code, not from better wording.
  • The recurring bug shape was always the same: a constraint stated in a prompt and trusted by the code around it.
References

DESIGN NOTES

Architecture
  • Eight coordinating skills — one orchestrator plus seven phase agents — over a JavaScript workflow that owns every gate decision.
  • Model tiers are pinned by the workflow, never self-reported by an agent, so reviewer independence is verifiable rather than claimed.
Documentation
  • The workflow reference states its own precedence: the script is the source of truth, and a diagram that disagrees with it is the bug.
  • Known gaps are documented as gaps — including which guarantees are enforced only by prompt.
Verification
  • The regression suite drives the real workflow against stubbed agents, exercising control flow rather than mocking it.
  • Fully offline — no API calls, no network — so the gates can be tested without spending a token.
